# Architectural Decision Records

Decisions that shape the implementation of [001-do-graph.md](./001-do-graph.md). These were extracted from the requirements specification to separate _what the system must do_ from _how we have chosen to build it_.

Source references follow 001-do-graph.md numbering.

---

## ADR-1: Single Durable Object for the entire graph

**Status:** Accepted

**Context:** The original specification was written to accommodate multi-tenant, workspace-scoped graph sharding with cross-shard edges, distributed reconciliation, and horizontal scaling via additional Durable Objects. In practice, we have one graph.

**Decision:** The system uses a single Durable Object instance to hold the entire graph. There is no workspace/tenant mapping, no subgraph sharding, and no cross-shard edge representation.

**Consequences:**
- No need for a shard routing layer or stable shard identifier derivation.[3][1]
- No cross-shard edges, so no duplicated summary rows or distributed traversal.[3][4]
- No cross-shard mutation coordination — no sagas, compensating actions, or async reconciliation.[4][3]
- No cross-shard consistency model — all mutations are serialized within the single DO.[1][2]
- Horizontal scaling via additional DOs is not a current concern.[4][3]
- If the graph outgrows a single DO in the future, sharding can be re-introduced as a new ADR.

**Supersedes these former requirements:**
- "The system shall map each logical workspace, tenant, or graph shard to a single Durable Object instance derived from a stable identifier."
- "The preferred default shall be one graph Durable Object per workspace or tenant."
- "If a workspace graph grows beyond acceptable limits for one Durable Object, the system shall support subgraph sharding."
- "Cross-shard edges shall be represented as references plus optional duplicated summary rows."
- "Mutations that span multiple shards shall use an asynchronous reconciliation strategy, saga, or compensating action pattern."
- "Across multiple shards, the system shall offer eventual consistency with explicit repair and retry semantics."
- "The system shall support horizontal growth by increasing the number of graph-owning Durable Objects."
- "The system shall preserve query locality as the primary scaling principle, favoring shard boundaries that keep hot traversals within one Durable Object."

## ADR-2: SQLite-backed Durable Object storage for canonical graph state

**Status:** Accepted

**Context:** Durable Objects support both KV-style storage and SQLite-backed storage. The graph workload requires transactional multi-row writes, indexed lookups, and relational queries over nodes, edges, and materialized summaries.

**Decision:** Canonical graph state (nodes, edges, lookup tables) is stored in SQLite-backed Durable Object storage.[2]

**Consequences:**
- Full SQL query capability for graph traversal and summary reads within the DO.
- Transactional writes across canonical rows and derived summary rows in a single operation.
- Storage is co-located with compute — no external round trips for hot reads.[2]
- Subject to DO SQLite storage limits; large payloads must live elsewhere (see ADR-3).

## ADR-3: R2 for large payloads, presigned-URL uploads

**Status:** Accepted

**Context:** Durable Object storage is optimized for coordination, metadata, and hot-path data. File uploads (documents, images, etc.) are part of the write workflow and must not be stored in DO SQLite or proxied through the Worker/DO. Cloudflare R2 provides S3-compatible object storage with no egress fees, and supports presigned URLs so clients upload directly.[5][3][8]

**Decision:** Files and other large payloads are stored in R2. Clients upload directly to R2 using presigned PUT URLs generated by the Worker. The graph Durable Object stores only a reference key, content type, size, and timestamp — never the file content itself.[3][8]

**Consequences:**
- DO storage costs stay proportional to graph structure, not payload size.[5]
- File uploads bypass the Worker and DO entirely — no 128 MB Worker request body limit, no billed DO wall-clock time for transfer.
- Upload flow is: request presigned URL -> upload to R2 -> confirm reference in graph. Orphaned R2 objects are cleaned by lifecycle rules.
- File reads require a round trip to R2 (or a presigned GET URL returned to the client).
- R2 has no egress fees, so long-lived clients reading files repeatedly are cost-safe.[8]

## ADR-4: WebSocket with hibernation as primary realtime transport

**Status:** Accepted

**Context:** The system needs persistent client connections for read-only subscriptions. Multiple client apps may hold long-lived connections for days or weeks, so idle cost is a primary concern. Cloudflare offers WebSocket hibernation to reduce billed idle duration.[7][6]

**Decision:** WebSockets are the transport for subscriptions. WebSocket hibernation is used to minimize cost from idle connections. Mutations are submitted over HTTP, keeping the socket protocol read-only and simple.[6][7]

**Consequences:**
- Read-only sockets — no request/response semantics, error handling, or idempotency required on the socket path.
- Hibernation allows the DO to sleep while sockets stay connected, reducing billed wall-clock time to near zero during idle periods.[7]
- Session metadata must be stored in WebSocket attachments to survive hibernation eviction (this remains a functional requirement in the spec).[6]

## ADR-5: Write-time materialization over read-time traversal

**Status:** Accepted

**Context:** The primary queries are bounded 1-3 hop neighborhood reads that would recompute the same traversal on every request if served dynamically. These queries are read-heavy relative to writes.

**Decision:** The system precomputes materialized summary tables at write time rather than traversing the graph at read time.[2]

**Consequences:**
- Read latency is determined by indexed table lookups, not traversal depth.
- Write latency increases slightly to maintain summary rows within the same transaction.
- Summary tables must be derivable from canonical edges; a repair tool is deferred until drift is observed in practice.
- Adding new query families requires defining new materialized views and write-path logic.
